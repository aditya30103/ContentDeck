# v3.9.3 — Production Audit

**Date:** 2026-04-07
**Tests:** 470 (unchanged — no regressions)
**Motivation:** After 2 months of incremental feature shipping, a brutal codebase audit surfaced 4 P0 data-corruption bugs, 4 P1 stale-state / misleading-response bugs, and 9+ silent failure paths — errors swallowed by `{}` or `void` with no Sentry visibility and no user feedback. This session fixed every confirmed issue.

---

## Phase 1 — P0 Fixes (data corruption / silent data loss)

### 1A: `refreshMetadata` cache clobber (`src/hooks/useBookmarks.ts`)
**Bug:** `const enriched = { ...bookmark, ...updates }` spread from stale closure. If the user changed areas/tags/notes between refresh start and DB write completing, those changes were overwritten in the TanStack Query cache.
**Fix:** Changed the `setQueryData` callback to use `{ ...b, ...updates }` (live cache entry from the map callback), then read the updated entry back for the `enriched` variable used by `autoSuggestTags`.

### 1B: arXiv content fire-and-forget (`src/hooks/useBookmarks.ts`)
**Bug:** `void db.from('bookmarks').update(...)` for arXiv abstract write — if the DB update failed, the user would see metadata (title, authors) but `content.text` would be silently missing. Reader mode and full-text search broken for that item with no indication of failure.
**Fix:** `await` the update inside a try/catch. On error: `console.error` + `Sentry.captureException`. No toast (non-critical to the user, but now visible in Sentry).

### 1C: `save-bookmark` latency — blocking `last_used_at` (`supabase/functions/save-bookmark/index.ts`)
**Bug:** `await adminClient.from('user_tokens').update({ last_used_at: ... })` was blocking the 201 response. If this write was slow or failed, the bookmarklet/iOS Shortcut would hang or error despite the bookmark already being saved successfully.
**Fix:** Changed to `void` (fire-and-forget). `last_used_at` is telemetry — the saved bookmark is the critical path.

### 1D: Area mutations missing error handling (`src/hooks/useBookmarks.ts`)
**Bug:** `assignArea`, `removeArea`, `setAreas` all had `if (error) throw error` with no callers catching them. Called with `void` from Dashboard.tsx — any DB error became a silent unhandled rejection. No Sentry, no toast, no cache rollback.
**Fix:**
- `assignArea`: on error, log to Sentry + toast (unless `code === '23505'` unique violation — expected on duplicate assignment); no throw
- `removeArea`: same pattern
- `setAreas`: snapshot `prev` before writes; on error, restore prev cache + Sentry + toast; no throw

## Phase 2 — P1 Fixes (stale state / misleading responses)

### 2A: Stale `areas` closure in enrichAndTag effect (`src/pages/Dashboard.tsx`)
**Bug:** `await autoSuggestTags(b, areas)` in the enrichAndTag effect used `areas` from the outer component scope, captured when the effect first ran. On first page load, `useTagAreas` query often hasn't resolved yet — `areas = []`. AI tagging would call the AI with no areas context, so suggestions could never match the user's taxonomy.
**Fix:** At the point of calling `autoSuggestTags`, read areas from the QueryClient cache directly: `const freshAreas = queryClient.getQueryData<TagArea[]>(['tagAreas']) ?? []`. If still empty, pass `undefined` so the hook reads from cache itself.

### 2B: `useUserValues` same-tab reactivity (`src/hooks/useUserValues.ts`)
**Bug:** The hook listened to the `storage` event to sync state, but `storage` only fires for cross-tab writes. When `ValuesOnboardingModal` wrote localStorage in the same tab, the hook state didn't update — `useScoring` read stale `null` values until page reload.
**Fix:** Added wrapper `updateValues` and `clearAll` functions that both call the localStorage helper AND call `setValuesState` directly for same-tab reactivity. The `storage` listener remains for cross-tab sync.

### 2C: `extract-content` returns 200 on failure (`supabase/functions/extract-content/index.ts`)
**Bug:** The catch block returned `jsonResponse({ status: 'failed', error: ... }, 200)`. Supabase's `functions.invoke()` only throws on network errors — HTTP 200 with a failure payload is invisible to the client. The client had no way to distinguish successful extraction from failed extraction.
**Fix:** Changed to HTTP 500. Also updated `triggerExtraction` in `useBookmarks.ts` to check `res.error` and log a Sentry breadcrumb when the edge function fails.

### 2D: `refreshMetadata` concurrent fire-and-forget race (`src/hooks/useBookmarks.ts`)
**Bug:** `void triggerExtraction(bookmark)` and `void autoSuggestTags(enriched)` fired concurrently. The AI was tagging using metadata-only context without waiting for content extraction to complete, so the AI never had article body text to work with.
**Fix:** `await triggerExtraction(bookmark)` first (in try/catch so AI tagging still runs on extraction failure), then `void autoSuggestTags(enriched)`. Matches the sequencing already used in `autoFetchMetadataAndTag`.

## Phase 3 — Silent Failure Hardening

### 3A: `metadata.ts` catch blocks (`src/lib/metadata.ts`)
Every external API call returned `{}` on failure with no logging — rate limits, API deprecations, network errors all invisible in production.
**Fix:** Added `console.warn('[metadata:source] description', err)` to every catch block (YouTube Data API, YouTube oEmbed, Twitter oEmbed, Microlink, arXiv edge function). Also added explicit `res.error` check in `fetchArxivMetadata` before the catch path.

### 3B: `autoSuggestTags` void calls (`src/hooks/useBookmarks.ts`)
All three `void autoSuggestTags(...)` call sites had no error handling. OpenRouter errors, invalid API keys, etc. were completely invisible.
**Fix:** Added `.catch(err => console.warn('[autoSuggestTags] failed', err))` to each void call site. Kept as fire-and-forget (no toast — this is background enrichment) but errors are now visible in the console.

### 3C: `triggerExtraction` result not checked (`src/hooks/useBookmarks.ts`)
`db.functions.invoke('extract-content', ...)` result was ignored entirely — even HTTP error responses were treated as success.
**Fix:** Check `res.error` after invoke. On error: `Sentry.addBreadcrumb` with category 'extraction'. Network-level errors also get a breadcrumb. `queryClient.invalidateQueries` only fires on success.

## Key Technical Decisions

**No toast for non-critical mutations.** arXiv content write failures, extraction failures, and AI tagging failures don't toast — they're background enrichment. But they now log to Sentry/console so production failures are visible without creating noise for users.

**Sentry breadcrumbs vs captureException for extraction.** Extraction failures are expected (paywalled articles, PDF-only content, rate limits). They don't represent code bugs. Using `addBreadcrumb` keeps them out of the Sentry issue inbox while preserving debug trails.

**`setAreas` rollback only on insert failure.** After delete succeeds but insert fails, the DB is now in an inconsistent state (areas deleted, insert incomplete). Cache rollback shows the user their previous state while the DB is inconsistent — they'll need to retry. The right fix would be a DB transaction, but junction table operations in Supabase client don't support transactions. Rollback + toast is the practical solution.

**`useUserValues` kept the storage event listener.** Some users open ContentDeck in multiple tabs. Cross-tab storage sync is still valuable — the wrapper functions handle same-tab writes as an additive fix.
