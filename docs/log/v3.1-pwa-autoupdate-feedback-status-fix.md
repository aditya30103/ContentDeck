## What Was Fixed

### 1. PWA forces delete/reinstall on every deploy (P0)

**Root cause:** The install handler in `sw.js` was a no-op — the new SW entered a
`waiting` state until the user tapped "Update Now" in UpdateBanner. On iOS standalone
PWA, the banner was often missed (or didn't appear reliably). Users concluded the app
was frozen on an old version and deleted the PWA from the home screen. Deleting the
PWA clears all associated localStorage, including the Supabase auth session, forcing a
full re-login with Google auth + 2FA every time.

**Fix:** Added `self.skipWaiting()` to the install handler. The new SW activates the
moment it finishes installing. The existing `controllerchange → window.location.reload()`
path in `UpdateBanner.tsx` handles the page refresh automatically — no user action
required. `window.location.reload()` does not clear localStorage, so the auth session
survives the update.

The UpdateBanner is now informational-only: spinning `RefreshCw` icon + "Updating to
latest version…" text visible for a split-second before the auto-reload fires. The
"Update Now" button and `handleUpdate` function were removed entirely.

Also fixed the backgrounded-PWA case: if `reg.waiting` is set on load (e.g. the SW
updated while the PWA was in the background), it now auto-posts `SKIP_WAITING`
immediately instead of just showing the banner and waiting for user action.

**Cache name:** bumped `contentdeck-v3.0.8` → `contentdeck-v3.0.9`.

### 2. Feedback status change not saving (P1)

**Root cause:** `FeedbackCard` controlled its `<select>` with `value={item.status}` (the
DB value from props). When the user picked "resolved", `handleStatusChange` fired and
set `showNoteInput = true` — but on the next React render, the select reverted to
"open" because `item.status` hadn't changed yet (the DB write hadn't happened).

`handleNoteSubmit` then tried to recover the selected status by reading it from the DOM
via `document.getElementById(`status-select-${item.id}`)?.value`. Because the select's
controlled value had already snapped back to "open", the DOM value was "open". So every
save silently sent `status: "open"` — appearing to succeed (optimistic update showed
"resolved" briefly) but immediately reverting on the `onSettled` refetch.

**Fix:** Added `selectedStatus` local state (`useState<FeedbackStatus>(item.status)`)
to control the select independently of the DB value. `handleStatusChange` sets
`selectedStatus`, `handleNoteSubmit` reads it directly — no DOM query needed. A
`useEffect` syncs `selectedStatus` back to `item.status` after DB refetches, so error
rollbacks are correctly reflected in the select too.

Removed the `document.getElementById` hack from `handleNoteSubmit` entirely.

## Key Decisions

### skipWaiting is safe for a personal single-user tool
The only downside of auto-activating a new SW is that it reloads the page mid-session.
For a personal productivity app deployed once-per-session, this is acceptable — and
far better than the delete/reinstall cycle that broke auth.

### Why the controlled-select bug was silent
The optimistic update in `updateStatus.onMutate` immediately set the cache to
`status: 'resolved'`, so the UI flickered to "resolved" briefly. Then `onSettled`
fired `invalidateQueries`, the DB refetch returned `status: 'open'` (the real saved
value), and the cache reverted. The whole round-trip was fast enough that the user just
saw "open" restored and assumed the save didn't work.

### useEffect for status sync
`useEffect(() => { setSelectedStatus(item.status); }, [item.status])` ensures the
select always reflects the authoritative DB value after any refetch. This covers: (a)
successful updates where item.status catches up to selectedStatus anyway, and (b) error
rollbacks where the optimistic update is undone and item.status reverts.
